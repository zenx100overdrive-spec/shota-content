## 1. 全体像：3本の「通信の筋道」とシステムアーキテクチャ

| 系統 | プロトコル | 入口 | 役割 |

| **A. LINE Messaging Webhook** | HTTPS POST + `X-Line-Signature` | `/line/webhook/shunkun` 等 | ユーザー発話 → AI応答 |

## 2. LINE Webhook通信ロジックと「Ack-Then-Process」パターン
2.1 リクエストライフサイクルとタイミング攻撃対策
LINEユーザーがメッセージを送信した瞬間、LINE PlatformからインフラへHTTPS POSTが叩き込まれる。
このWebhookを処理する上で、セキュリティと速度のトレードオフを回避する設計が以下である。

```
[LINE Platform]
    │  HTTPS POST
    │  Header: X-Line-Signature: <Base64(HMAC-SHA256(body, channel_secret))>
    │  Body:    raw JSON bytes（events配列）
    ▼
[Render Edge → uvicorn → FastAPI]
    │
    ├─ RequestGuardMiddleware      … パストラバーサル拒否、POSTサイズ上限制限
    ├─ RateLimitMiddleware        … Webhookは 300 req/min/IP でDDoS・誤爆を遮断
    ├─ SecurityHeadersMiddleware  … HSTS, X-Frame-Options等の硬質化
    ├─ CORSMiddleware             … 許可された店舗ドメイン限定
    ▼
[Route Handler] 例: line_shunkun_webhook()
    │
    ├─ body = await request.body()          … ★ JSONパース前に raw bytes 取得（署名検証の鉄則）
    ├─ verify_signature(body, X-Line-Signature)
    │     └─ HMAC-SHA256 → Base64 → hmac.compare_digest（タイミング攻撃を完全に無効化）
    ├─ handle_line_webhook(body)
    │     └─ json.loads → events[] を安全に走査
    │           ├─ type=follow  → welcome Reply + 無料体験チケット付与
    │           └─ type=message
    │                 ├─ gate_zero_balance()   … チケット残高をSQLiteからミリ秒でチェック
    │                 ├─ safe_reply("処理中…")  … ★ Reply API（reply_tokenを数秒以内に消費）
    │                 ├─ spawn_background(job)  … ★ asyncio.create_task で重い処理をデタッチ
    │                 └─ return {"status":"ok"}   … ★ Webhook HTTP 200 返却（LINE PlatformへのACK）
    │
    └─ [Background Task (Fire-and-Forget)]
          ├─ Gemini API / 各専用プロセッサ実行（最大数10秒の推論フェーズ）
          ├─ consume_ticket()（正常完了時のみデクリメント）
          └─ client.push(userId, 解析結果)  … Push API（reply_token不要、非同期完了後に能動送信）
```

2.2 署名検証の共通基盤コード
JSONとしてパースする前に、リクエストの raw bytes を直接引っこ抜いて検証するのが鉄則だ。文字列比較によるタイムレイテンシの隙を突く「タイミング攻撃」をパージするため、hmac.compare_digest を採用している。

```Python
def verify_signature(self, body: bytes, signature: str | None) -> bool:
    if not self.channel_secret or not signature:
        return False
    digest = hmac.new(
        self.channel_secret.encode("utf-8"),
        body,
        hashlib.sha256,
    ).digest()
    expected = base64.b64encode(digest).decode()
    return hmac.compare_digest(expected, signature)
```


    
2.3 asyncio.create_task によるバックグラウンド分離
LINEのWebhookは「3秒以内」にレスポンス（HTTP 200 ACK）を返さなければ、再送ループに陥る脆弱性を持つ。LLM（Gemini）の推論を待っていては絶対に間に合わない。
そのため、受付（Reply）と調理（Gemini + Push）を完全に非同期分離（Fire-and-Forget）している。

```Python
def spawn_background(coro: Coroutine[None, None, T], *, label: str = "line_bg") -> asyncio.Task[T]:
    """Webhook即返却後に、裏でLLMを回してPushするための非同期タスクラッパー"""
    async def _wrapper():
        try:
            return await coro
        except Exception as e:
            logger.error(f"[{label}] Background task failed: {e}", exc_info=True)
    return asyncio.create_task(_wrapper())
```
## 3. Render Starterインフラと「0秒起動」の論理
インフラ層には、Renderの Starterプラン を採用。個人開発でよく使われるFreeプランをあえてビジネス目的でパージした理由は、UXにおけるコールドスタートの根絶だ。

Freeプランの脆弱性: 一定時間アクセスがないとインスタンスがスピンダウン（休止状態）し、次のリクエスト時に 50秒以上のコールドスタート（起きるまでの待ち時間） が発生する。LINEのWebhook仕様において、これは即タイムアウト・システム沈黙（バグ）を意味する。

Starterプランの論理: 常時起動（Always-On）を保証。プロセスがメモリ上に常駐しているため、ファーストレイテンシは常に数十ミリ秒に収束する。

render.yaml のBlueprint設定および起動コマンドは以下の通り。

```YAML
services:
  - type: web
    name: zdna-official
    env: python
    plan: starter # 常時起動・メモリ確保
    startCommand: python -m uvicorn main:app --host 0.0.0.0 --port $PORT --workers 1 --log-level debug
    healthCheckPath: /health
```

【あえて workers=1 のシングルプロセスに絞る理由】
CPUコアをフルに使って workers を増やさないのは、インメモリで行う Rate Limit（速度制限）の状態監視をプロセス間で分散させないため、およびRender Starterのメモリ上限枠内で 12体分のBotモジュール（MediaPipe連携や重いプロンプトアセット群）を安定して完全リークレスで稼働させるための論理的最適化である。

## 4. Multi-Tenant by LINE Channel と Stripeイベント駆動型アーキテクチャ
4.1 12体のBotを混線させない「論理分離モデル」
12体のBotはすべて同じFastAPIインスタンス上で動いているが、完全にマルチテナント化されている。
Webhookへの入り口は /line/webhook/{slug} で動的にルーティングされ、各Bot固有の channel_secret と access_token をマッピングした LineMessagingClient インスタンスへ処理が移譲される。

瞬殺君（shunkun）の内部のみ、入力されたコンポーネント（URL、画像、音声、テキスト）に応じた Content-Based Dispatch（サブルーティング） を行い、専用Bot（bot005 瞬殺リサーチ等）は、入り口から直接単一の専用Processorに直結する。

4.2 Stripe Webhook による冪等なチケット付与フロー
決済はLINE Botのルーティングとは完全に別系統のイベントバスとして構成。Stripeの checkout.session.completed イベントを検知し、データ永続化層（SQLite）の残高（Ledger）を非同期に更新する。

```コード スニペット
sequenceDiagram
  participant U as ユーザー (User)
  participant W as 要塞ストア / LINE
  participant F as FastAPI (main.py)
  participant S as Stripe Server
  participant DB as SQLite (data/)

  U->>W: チケット購入ボタンをトリガー
  W->>F: POST /api/tickets/checkout
  F->>S: Stripe Checkout Session作成 (metadataにline_user_idを埋め込み)
  S-->>U: 決済ページURLへリダイレクト
  U->>S: クレジットカード決済完了
  S->>F: POST /stripe-webhook (イベント: checkout.session.completed)
  F->>F: stripe.Webhook.construct_event による厳密な署名検証
  F->>F: process_checkout_completed()
  F->>DB: LINEユーザーIDに紐づくチケットをSQLiteに安全に書き込み
  F->>W: LINE Messaging API経由でユーザーへ「チャージ完了」をPush通知
```
【Stripe at-least-once配信に対する冪等性（Idempotency）保証】
ネットワークの瞬断等により、Stripe Webhookは同一の決済イベントを複数回送信（at-least-once）してくる可能性がある。
二重チャージという致命的なバグを防ぐため、システム側では lookup_entitlement_by_session ロジックを噛ませ、処理済みの session_id をキャッシュ・DBレベルで突合して弾く、冪等なFulfillment（履行）を徹底している。
